# W01 — Prior art: how existing graph workflow engines solve I/O, errors, and retry

Research for [issue #19](https://github.com/Max-Levitskiy/skills/issues/19), a child of the `workflow` plugin map ([issue #18](https://github.com/Max-Levitskiy/skills/issues/18)).

Path note: no existing convention for research docs was found in this repo (`docs/` has `superpowers/`, `agents/`, `orchestration/`, `proposals/`, but no `research/`), so this file establishes `docs/research/YYYY-MM-DD-<slug>.md` as the location for standalone prior-art research.

## Method

This is evaluative, not a tutorial. Each section states one of our already-locked `workflow` design decisions, then checks it against concrete, named, primary-sourced mechanisms in existing engines — never a bare "some engines differ." Section 0 is in-repo evidence: `plugins/herdr` already ships a production ACS (Agent Config Standard) implementation of a named, launchable, config-overridable binding — the closest thing this marketplace has today to our `agent` Action kind — built under the same constraints (Bun, zero runtime dependencies) as `workflow` will be. Sections 1–6 survey external engines: LangGraph, Temporal, Argo Workflows, GitHub Actions, n8n, Prefect, Dagster, Airflow, AWS Step Functions.

## 0. In-repo prior art — herdr's `agent` Action kind (`plugins/herdr`)

herdr's subagent-preset system (`plugins/herdr/skills/herdr/scripts/lib/config.ts`, `plugins/herdr/skills/herdr/scripts/herdr-agent.ts`) is a production implementation of exactly the pattern our `agent` Action kind proposes: a named, launchable slot with a default binding, overridable per config layer. It was built under our same constraints (Bun, zero runtime dependencies, no `dot`/native binary required), so it outranks the external engines below where the two speak to the same decision.

**Findings:**

- **Named slot + default binding + key-by-key config override — Agrees.** `AgentPreset` (`plugins/herdr/skills/herdr/scripts/lib/config.ts:24-62`) is exactly our Action shape: `command`, `cwd`, `env`, plus launch-specific fields (`session`, `split`, `focus`, `bootTimeoutMs`, `replyTimeoutMs`, `readLines`, `replyMarker`, `composerMarker`, `chrome`). Eight presets ship as `BUILTIN_AGENTS` (`config.ts:83-110`) so the tool works with zero config; `agents()` (`config.ts:136-142`) layers a user's `agents.<name>` entry over the built-in with the same name via `{ ...BUILTIN_AGENTS[name], ...(c.agents?.[name] ?? {}) }` — literal per-key override, matching ACS v1's documented "deep merge... arrays replace wholesale" rule (`standards/agent-config.md:32-38`). `resolvePreset()` (`config.ts:153-169`) then resolves one named preset into what a launch needs, refusing to guess a neighbour on a typo. This is our "named slots with a default binding; a config layer can rebind a name key by key" decision, already shipped and exercised — not a design sketch.
- **Kind-rebinding across `cmd`/`skill`/`agent`/`human` — Wrinkle (unvalidated by this evidence).** `AgentPreset` has no `kind` field at all (`config.ts:24-62` — the full interface). Every preset, built-in or user-defined, is the same mechanism: spawn `command` as a process attached to a herdr pane, then scrape its TUI screen. Overriding a preset can change *which binary* runs (e.g. `reviewer` overriding `claude`'s argv with `--permission-mode plan`, per `references/agents.md:106-118`), but it can never change *how* it runs — there is no path from an `agent`-kind slot to a `cmd`-kind or `human`-kind binding in herdr's model, because herdr's whole domain is "launchable TUI subagents." Our locked decision that a config layer can rebind a name's **kind**, not just its command, has no in-repo precedent to validate it: the one production Action-like system we have never needed to solve cross-kind rebinding, because it only ever had one kind.
- **Schema at the agent boundary — Contradicts.** herdr has no schema anywhere on the `agent` boundary, declared or otherwise. `cmdStart`'s `--prompt` is typed verbatim into a TUI composer (`typeInto`, `herdr-agent.ts:308-318`), and `converse()` returns whatever `extractReply()` scrapes back out (`herdr-agent.ts:236-269`) — a plain `string`, produced by cutting the screen at the last full-width rule, skipping the echoed prompt, skipping past a `replyMarker` (`⏺` for Claude Code, `•` for Codex — per-preset regexes, not schema fields), and stripping TUI furniture (`chrome` regexes). There is no JSON parse, no field, no `required`, nowhere a preset or a caller declares "the reply must have shape X." Our decision that "every boundary declares a schema, including agent boundaries — prose is only an extra constraint layered on the same fields, never a substitute" is not what herdr does today: its entire `agent`-kind contract is "whatever text survives the TUI scrape." This is a concrete engineering reason, not an oversight — a TUI is not a JSON emitter, so a schema-validating `agent`-kind Action would need either (a) instructing the agent in its prompt to close with a fenced JSON block matching the node's declared schema and parsing only that out of the scraped text, or (b) a genuinely non-interactive one-shot invocation instead of pane+TUI scraping. herdr already proves route (b) is available as a separate code path: `herdr-agent.ts start <preset> --prompt "..."` is already a one-shot ask+reply round trip (`cmdStart`, `herdr-agent.ts:454-503`), so a schema-validating wrapper could sit on top of its raw string return without touching the TUI-scraping internals used for multi-turn `ask`.
- **Standard error shape on a `[on="failed"]` edge — Wrinkle.** herdr's only failure signal is `die()` (`herdr-agent.ts:54-57`): `console.error(msg); process.exit(1)`. Every failure path — unresolvable preset (`config.ts:158-163`), missing `command` (`config.ts:164-166`), a pane that never finished booting (`herdr-agent.ts:474-476`), a reply that never went quiet (`herdr-agent.ts:353-356`), a message that was never delivered (`herdr-agent.ts:374-379`) — funnels into the same free-text-to-stderr-plus-exit-1 shape. There is no structured error object (no error code, no distinction between "config problem" vs "the agent itself failed" vs "transport timed out"). If an `agent`-kind Action reused herdr's mechanics as-is, the "standard error shape" our `[on="failed"]` edges are supposed to carry would have to be synthesized by the calling agent parsing free-text stderr, not supplied by the mechanism itself — a real gap between what we've locked in and what the one in-repo Action-like implementation actually returns on failure.
- **Timeouts as per-Action config — Agrees.** `bootTimeoutMs`, `replyTimeoutMs`, and `readLines` are literal fields on `AgentPreset` (`config.ts:39-44`), with built-in defaults (`BUILTIN_DEFAULTS`, `config.ts:112-121`: `bootTimeoutMs: 90_000`, `replyTimeoutMs: 300_000`) that a preset or a `--timeout` flag can override (`cmdStart`, `herdr-agent.ts:473`: `f.timeout ?? preset.bootTimeoutMs ?? 90_000`). This is exactly our locked framing of herdr as prior art — "launchable agent presets... with `command`, `cwd`, `env`, and timeouts per preset" — already true of the shipped code, not aspirational.
- **Retry kept out of Action config — Agrees, weakly.** `AgentPreset` has no retry-count or backoff field anywhere (`config.ts:24-62`, exhaustively). The one retry-shaped constant in `herdr-agent.ts`, `SUBMIT_ATTEMPTS = 3` (`herdr-agent.ts:42`, used in `converse()` at `herdr-agent.ts:336-351`), is a transport-level delivery retry — confirming a keystroke's Enter actually landed in the TUI composer — not a semantic "the agent's answer was wrong, redo the work" retry; it operates below the level our Action abstraction even reaches, on pane I/O reliability, not task correctness. herdr never introduced a config-based "retry the agent" knob despite having every opportunity to (the `bootTimeoutMs`/`replyTimeoutMs` pattern was right there to copy) — soft supporting evidence that the one artifact actually built under our exact constraints didn't reach for engine-level retry config, though it's weak evidence precisely because herdr doesn't orchestrate multi-node workflows at all, so the question of "redo a failed step" never arises for it in the first place.

## 1. Static Lint-Time Schema Checking with Width Subtyping

**Our decision:** Edge/task compatibility is checked statically at lint time (before any run) via width subtyping — extra producer fields are fine, missing required fields are a lint error — so the consumer never re-checks the schema at runtime.

**Findings:**

- **Dagster** — `DagsterType` + `type_check_fn`, explicitly framed by Dagster's own docs as a *runtime* mechanism, not a static one. The docs page states outright: "Dagster includes facilities for typing the input and output values of ops ('runtime' types)." A `type_check_fn(context, value) -> bool | TypeCheck` runs when data actually flows through an op's `In`/`Out` during a job run; a failing check raises `DagsterTypeCheckDidNotPass` mid-execution, not before. Dagster is often cited as the standout for typed dataflow between steps, but its actual mechanism is per-run dynamic dispatch over live values, closer to our rejected "consumer checks at runtime" model than to our lint-time bet — the closest thing to a static check is generic `mypy`/type-hint checking of the *Python function signatures*, which is a language-level property (like Temporal below), not an engine-level graph check. Source: [Dagster `types` API docs](https://docs.dagster.io/api/dagster/types).
- **LangGraph** — `StateGraph(Schema)` + `.compile()`. `TypedDict`/dataclass schemas carry *no* runtime enforcement at all (Python passes dicts through unchecked); only `mypy` catches mismatches, and only if you run it. Pydantic `BaseModel` schemas add real validation, but it fires *only* at the single entry boundary — `graph.invoke()` — not per-node-edge, and not before the run: a `ValidationError` on bad input is raised at invoke time, and intermediate node-to-node data is never re-validated by the framework at all. `.compile()` checks graph topology (dangling nodes, unreachable states) but not schema compatibility between producer and consumer nodes. There is no lint-time, edge-level field check anywhere in the pipeline. Source: [LangGraph `use-graph-api` docs](https://docs.langchain.com/oss/python/langgraph/use-graph-api).
- **Temporal** — Workflow→Activity calls are type-checked by the host language's compiler (`proxyActivities<T>()` in TypeScript, `@ActivityInterface`-annotated stubs in Java, static function types in Go), which is a real static check, but it is a *client-language* property, not an engine-level one: the graph itself doesn't have a schema layer independent of the SDK language. Crucially, this static guarantee stops at the wire boundary — every call is marshalled through the `DataConverter` into an opaque `Payload` (bytes), and a workflow calling an activity via untyped helpers (raw activity name + `Map`/`RawValue` payload) or a custom `DataConverter` bypasses the compiler entirely, degrading to a runtime deserialization failure on the worker. So Temporal's real edge check is "static if you use the typed stub API, silently unchecked if you don't," with no lint step that catches the second case ahead of time. Source: [Temporal `dataconversion` docs](https://docs.temporal.io/dataconversion).
- **GitHub Actions** — `on.workflow_call.inputs.<id>.type` (one of `string`/`number`/`boolean`) is the only prior-art mechanism that resembles a real static gate: if a caller's `with:` value doesn't match the callee's declared type, the run fails before any job step executes. But this check happens at *workflow-run dispatch* time (when the run starts), not at a separate pre-run lint/compile pass the way `argo lint` or our own lint command runs independently of triggering an execution — there's no equivalent of "validate this graph offline, no run created." Composite actions (`runs.using: composite`, defined in `action.yml`) are strictly worse: inputs have no `type` field at all, everything is a string, and a missing/mismatched field is only ever discovered inside a `run:` step's shell logic. Source: [GitHub Actions "Reuse workflows"](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows).
- **Argo Workflows** — `argo lint` is a real pre-submission static pass (also runnable `--offline`, i.e., without a cluster), and it catches YAML/schema-shape errors. But it does **not** perform field-presence checking on `{{inputs.parameters.x}}` templating: a `template` that references an undeclared or unbound parameter passes lint cleanly and only fails when the controller evaluates the string substitution at execution time, typically manifesting as an empty string or a runtime evaluation error deep in a DAG/step. `argo lint` also cannot fully validate `templateRef`-based parameter matching against `WorkflowTemplate`s without live cluster access (`--offline` skips that check). So Argo has a lint phase but its width-subtyping-equivalent (declared vs. bound parameters) is explicitly not covered by it — a documented gap, not an oversight fixed later. Source: [Argo Workflows parameters walkthrough](https://argo-workflows.readthedocs.io/en/latest/walk-through/parameters/).
- **AWS Step Functions** — `ValidateStateMachineDefinition` API is the closest prior-art analogue to a pure lint pass: given an ASL JSON document it returns `OK`/`FAIL` plus diagnostics for malformed JSONPath/JSONata syntax and bad state transitions, runs with zero deployed resources, and is designed to sit in CI pre-commit hooks — structurally similar to our lint step. However it validates *syntax and reachability*, not field-presence compatibility between a producer state's `ResultPath`/`Parameters` output shape and a downstream state's `InputPath` reference; that gap is instead covered by a separate, opt-in `TestState` API that mocks a single state and inspects data-flow transformations at `DEBUG` inspection level — i.e., AWS split "is this well-formed" (static) from "does this data actually flow correctly" (a manual, per-state runtime simulation) rather than unifying both into one lint-time width-subtyping check. Source: [`ValidateStateMachineDefinition` API reference](https://docs.aws.amazon.com/step-functions/latest/apireference/API_ValidateStateMachineDefinition.html).
- **Airflow** — XCom is the clearest "no static bet at all" case among these engines. `@task`-decorated function return-type hints (e.g. `-> dict[str, int]`) are accepted by the TaskFlow API but are documented as carrying no enforcement: "Standard Airflow does not enforce runtime type validation or parse-time type checking out-of-the-box just because you added a type hint." A downstream task can `xcom_pull()` a value of any shape the JSON (or, if `enable_xcom_pickling=True`, pickle) serializer accepted, and a field-shape mismatch is discovered only when the consuming task's code touches the missing/wrong-typed field mid-run. There is no DAG-level compile step that inspects XCom key shapes across task boundaries at all. Source: [Airflow XCom core-concepts docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/xcoms.html).
- **n8n** — Same "no engine-level bet" story as Airflow, via a different mechanism: `INodeExecutionData[]` is a bag of loose `json` objects passed between nodes with no declared per-node input/output schema in the `INodeType` interface itself. Any schema enforcement (e.g., via `ajv.compile()`) is something an individual node author bolts on manually inside their own `execute()` function; n8n's core has no facility to compare one node's declared output shape against the next node's declared input shape, before or during a run. Source: [n8n community: node data validation](https://community.n8n.io/t/using-n8n-nodes-data-validation/44093).

**Verdict:** Wrinkle — Dagster, the engine most likely to be assumed as "the static-typing one," documents its own `DagsterType` system as explicitly *runtime*, and every other surveyed engine either checks nothing (Airflow, n8n), checks only the entry boundary (LangGraph's Pydantic validation on `invoke()`), or checks structural/syntactic well-formedness without checking producer/consumer field compatibility (Argo's `lint`, AWS's `ValidateStateMachineDefinition`). GitHub Actions' `workflow_call` typed inputs is the one mechanism that is a genuine pre-execution type gate, but it fires at run-dispatch rather than at an independent, run-free lint pass — meaning our decision to run a true offline lint that proves width-subtyping compatibility across every edge before any run exists has no direct prior-art precedent; we are the outlier, not a follower, on this specific bet.

## 2. Error Routing: Handler Nodes, Callbacks, and Retry Policies

**Our decision:** An error handler is just an ordinary node reached by an outcome edge (`[on="failed"]`); no engine-level retry policy exists as a distinct concept — `failed` is an ordinary outcome like any other, dispatched the same deterministic way as any other edge.

**Findings:**

- **Temporal** — `RetryPolicy` is a config object attached to `ActivityOptions`/workflow execution options (fields: `InitialInterval`, `BackoffCoefficient`, `MaximumAttempts`, `NonRetryableErrorTypes`), completely outside the workflow's code/graph. Retryability is resolved two ways: the caller lists string error types in `NonRetryableErrorTypes` on the policy, or the activity throws an `ApplicationError` with `nonRetryable`/`non_retryable=True` set at the throw site (`ApplicationFailure.nonRetryable` in TS, `temporal.NewNonRetryableApplicationError` in Go) — the throw-site flag always wins over the policy list. None of this is visible as workflow structure: retries are invisible engine machinery recorded only as `ActivityTaskStarted`/`ActivityTaskFailed` events in Event History, inspectable only by querying/replaying history, never by reading the workflow definition. Source: [Temporal docs — Non-retryable errors](https://docs.temporal.io/design-patterns/non-retryable-errors), [Temporal Failures reference](https://docs.temporal.io/references/failures).
- **AWS Step Functions** — Two separate mechanisms sit on the same `Task`/`Parallel`/`Map` State. `Retry` is a policy array (`ErrorEquals`, `IntervalSeconds`, `MaxAttempts`, `BackoffRate`) evaluated first and never itself becomes a `Next` transition — pure policy object, like Temporal's. `Catch` is genuinely edge-like: each catcher is `{ErrorEquals: [...], Next: "StateName", ResultPath}`, and a match transitions execution to a real named state exactly the way our `[on="failed"]` edge dispatches to a node. Unlike our single generic `failed` outcome, `ErrorEquals` lets one state declare several parallel catch-edges keyed to distinct named error types (`States.Timeout`, `States.Permissions`, custom exception names, or the `States.ALL` wildcard, which must be the last, standalone catcher) — effectively N outcome-labels per failure, not one. Source: [AWS Step Functions — Error handling in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html).
- **GitHub Actions** — `continue-on-error: true` on a step or job is pure suppression, not routing: it forces the step's `conclusion` to `success` even though its `outcome` stays `failure`, and subsequent steps run as if nothing happened — there is no node/edge here at all, just a boolean that erases the failure signal unless a later step explicitly reads `steps.<id>.outcome`. `if: failure()` is the closer analog to our outcome edge: it's a conditional gate re-evaluated on each subsequent step, letting that step run specifically because an earlier step failed. The key structural difference is that `failure()` is a job-scoped aggregate (true if *any* previous step in the job failed) rather than a label on a specific edge from one specific predecessor node — GitHub Actions has no per-edge failure label, only a global predicate plus manual `steps.<id>.outcome`/`steps.<id>.conclusion` lookups to narrow it to one specific ancestor. Source: [GitHub Actions — Workflow syntax reference (`continue-on-error`)](https://docs.github.com/actions/using-workflows/workflow-syntax-for-github-actions), [GitHub Actions — Contexts reference (`steps.<id>.outcome`/`conclusion`)](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts).
- **Argo Workflows** — `retryStrategy` (fields: `limit`, `retryPolicy: "OnFailure"`, `backoff.duration`/`backoff.factor`) is a policy object on a DAG task or template, structurally identical to Temporal's/Step Functions' retry policies — individual retry attempts happen inside the node, invisibly to the graph. `onExit` is node-like — it names an ordinary template (`onExit: <template-name>`, or `spec.onExit` at the workflow level) — but it is not reached by a `[on="failed"]` edge: it is a designated lifecycle slot that fires unconditionally after the task/workflow's *final* outcome is settled (success, failure, or error alike), comparable to a `finally` block, not a failure-only branch. To get failure-only behavior the `onExit` template itself must branch internally on `{{tasks.<name>.status}}` or `{{workflow.status}}` — i.e., outcome-based dispatch happens via string templating *inside* the handler node rather than being expressed as a graph edge, which is exactly the guard-language-inside-the-node approach our design explicitly rejects for edge dispatch. Source: [Argo Workflows docs — Retries](https://argo-workflows.readthedocs.io/en/latest/retries/), [Argo Workflows docs — Fields reference (`onExit`)](https://argo-workflows.readthedocs.io/en/latest/fields/).
- **Airflow** — `on_failure_callback` is a plain Python callable attached to a task or DAG, invoked out-of-band on failure; it is not a task/node and never appears in the DAG graph. `trigger_rule=TriggerRule.ONE_FAILED` is the closest real analog to our failed-outcome edge: it lets a genuine downstream **task** (a real DAG node) execute specifically because at least one direct upstream task entered `failed`/`upstream_failed` state, without waiting for the rest of the upstream tasks. The load-bearing difference: `trigger_rule` is a property of the *downstream* node evaluated against the aggregate states of *all* its direct upstream tasks (not a label on one specific incoming edge from one specific upstream node), so it can't express "only run because *this particular* upstream node failed" when there are multiple upstream parents — only "some/all/one of them failed." It also decouples "handled" from "the run's overall status": a `ONE_FAILED` task that runs and doesn't itself raise is marked `success`, so the DAG run can still show green unless that task explicitly does `raise AirflowException(...)`. Source: [Airflow docs — Trigger Rules](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html).

- **Prefect** — `retries`/`retry_delay_seconds` are decorator config on `@task`/`@flow`, an out-of-band policy exactly like Temporal's. `on_failure=[...]` is a list of plain callback functions `(entity, run, state)` fired on state transitions; Prefect's docs state these hooks explicitly do **not** fire on intermediate retry attempts, only once retries are exhausted and the run reaches `Failed`. Neither mechanism is a graph node — both are config/callbacks bolted onto the task, with no analog to a routable failure node. Source: [Prefect docs — State-change hooks](https://docs.prefect.io/v3/how-to-guides/workflows/state-change-hooks).
- **Dagster** — `Failure` is an exception class you `raise` inside an op with structured `metadata`; `@failure_hook` is a callback bound at the job/op level via `hooks={...}`, receiving a `HookContext` with `op_exception`. Both are callback/exception machinery, not graph nodes; Dagster's own docs point failure-handling outside the op graph entirely for run-level cases ("Run Failure Sensors"), so Dagster has **no** node-like failure primitive inside a job's op graph. Source: [Dagster docs — Op hooks](https://docs.dagster.io/guides/build/ops/op-hooks).
- **n8n** — The dedicated **Error Workflow** is node-like (triggered by a first-class `Error Trigger` node) but structurally decoupled from the failing workflow's own graph: it's a wholly separate workflow selected via Settings → "Error workflow," invoked on any node failure, not reached by an edge inside the original DAG. Per-node **Continue On Fail** instead swallows the error locally (optionally through a real second "error output" pin, which is graph-edge-like) and forces the execution to report success — which n8n's own docs/community warn means the global Error Workflow will **not** fire for that node, making the two failure-routing mechanisms mutually exclusive per node. Source: [n8n docs — Handle errors gracefully](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully).
- **LangGraph** — `add_conditional_edges` only branches on **state fields**, so error routing-by-edge requires a node to catch its own exception in a `try/except` and write an error flag to state for the router to read; an *uncaught* exception instead propagates as an ordinary Python exception out of `.invoke()`/`.stream()`, aborting the run with no routable "failed" graph state produced. Separately, `add_node(..., error_handler=...)` (langgraph>=1.2) is a callback invoked with a `NodeError` only after `RetryPolicy` is exhausted, and it can return `Command(goto="node_name")` to redirect execution — a callback whose effect mimics an edge, not a declared edge itself. Source: [LangGraph docs — Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance).

**Verdict:** Wrinkle — AWS Step Functions' `Catch`→`Next` and Airflow's `TriggerRule.ONE_FAILED` both prove node-reachable failure routing is a real, load-bearing pattern elsewhere, but both attach the routing rule to a *state* (multiple `ErrorEquals` types per catcher, or an aggregate-over-all-upstream-parents trigger rule) rather than labeling a specific edge the way ours does, and Airflow shows that reaching a failure-handling node doesn't automatically make the *run's* overall status reflect the failure unless the handler explicitly re-raises — a gap our "unhandled `failed` becomes `halted`" rule should guard against for handler nodes that quietly succeed.

## 3. Retry as a Graph Edge vs. Config/Policy

**Our decision:** Retry is deliberately IN THE GRAPH — an edge from a node back to itself (or an earlier node) with an explicit limit, so retry is visible, boundable, and inspectable as a real edge, with no hidden engine-level retry policy.

**Findings:**

- **Temporal** — `RetryPolicy` attached to an Activity (or, rarely, a Workflow), invisible in the workflow's own control-flow graph. Temporal's docs explicitly warn that retrying a whole *Workflow Execution* (as opposed to individual Activities) is "not recommended due to the deterministic nature of Workflow replay": because replay re-runs the same sequence of events, a workflow-level retry re-executes already-completed Activities and their side effects, and Temporal's own idempotency guidance (Workflow Run ID + Activity ID as a stable idempotency key, unique-constraint inserts, non-retryable `ApplicationFailure` types) exists specifically to paper over the fact that the policy has no notion of "already did this" at the graph level. The default `MaximumAttempts` is literally unlimited (`0` means infinite) unless a human remembers to bound it. Source: [Temporal — What is a Retry Policy?](https://docs.temporal.io/encyclopedia/retry-policies).
- **AWS Step Functions** — the `Retry` field (`ErrorEquals`, `IntervalSeconds`, `BackoffRate`, `MaxAttempts`, `MaxDelaySeconds`) is a property of a `Task`/`Parallel`/`Map` state, not a transition in the Amazon States Language graph — a retried state never appears as a distinct `Next` target, so nothing in the ASL definition shows a loop. Yet the docs state plainly that "Retries are treated as state transitions" for billing, and separately that the execution history is a **hard, non-negotiable quota of 25,000 events**; hitting it mid-execution (e.g. from a heavy-retry loop) makes "the execution … fail" outright, with the only documented mitigation being to redesign around Distributed Map / nested state machines rather than raise the quota. Retry-as-policy is thus invisible in the definition but still metered against a hard structural ceiling. Source: [Handling errors in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html) and [Step Functions service quotas](https://docs.aws.amazon.com/step-functions/latest/dg/service-quotas.html).
- **GitHub Actions** — has no config-based retry primitive at all for an individual step; there is no `retry:` key in workflow YAML. The documented workaround is the third-party `nick-fields/retry` action, which only works by shelling out a `command:` string — it explicitly "cannot wrap other `uses` actions directly" (e.g. `actions/checkout@v4`), forcing users either to reimplement the action as a CLI call or to hand-write a bash `until` loop. This is a genuine gap, not a design choice: GitHub Actions' `needs:` dependency graph has no mechanism, native or edge-like, for expressing "try this node again" — it is entirely off-graph, ad hoc script logic. Source: [nick-fields/retry](https://github.com/nick-fields/retry) (README documents the `command`/`uses` limitation).
- **Argo Workflows** — `retryStrategy` (`limit`, `retryPolicy`, `backoff.duration/factor/maxDuration/cap`, `expression`) is config attached to a template, exactly the pattern we rejected. But the controller's actual execution mechanics don't hide the attempts: verified directly in source, each retry attempt is materialized as a genuinely distinct child node, named `fmt.Sprintf("%s(%d)", retryNodeName, retryNum)` and attached via `addChildNode`, so `status.nodes` ends up with `my-task(0)`, `my-task(1)`, … as separate entries with independent `phase`/pod records even though they share one `displayName`. Config-driven retry, in other words, still had to reinvent per-attempt node identity to stay inspectable. Source: [argo-workflows `operator.go`, lines 2539–2542](https://github.com/argoproj/argo-workflows/blob/main/workflow/controller/operator.go#L2539-L2542) (retry node naming), corroborated by the [Retries docs](https://argo-workflows.readthedocs.io/en/latest/retries/) and [Node Field Selectors docs](https://argo-workflows.readthedocs.io/en/latest/node-field-selector/) (`name` vs `displayName` disambiguation).
- **Airflow** — `retries`/`retry_delay` are per-task config, and the docs document a sharp, easy-to-miss consequence: "If the first task was not successful then on every retry task XComs will be cleared to make the task run idempotent. XComs therefore can't be used to persist state across task retries or Sensors poke." This is an invisible side effect of the config model — nothing in the DAG definition tells you that a task's own outputs get wiped between attempt N and N+1; you only discover it when code that assumed persisted partial state breaks on retry. Source: [Airflow — XComs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/xcoms.html) ("XComs" section, retry-clearing note).

**Verdict:** Wrinkle — Argo's `retryStrategy`, though config-driven exactly like the others, still has to synthesize a distinct child node (`name` suffixed `(%d)`) per attempt purely to stay inspectable, which is direct evidence *for* our approach but also a concrete implementation obligation: an edge revisiting the same node needs a per-attempt run-state record, not just a re-executed node with no attempt history — while Temporal's own warning against whole-workflow retry, Step Functions' invisible-retry-vs-hard-history-quota interaction, Airflow's silent XCom wipe on retry, and GitHub Actions' complete absence of a native retry primitive all independently document the failure modes (duplicate side effects, quota exhaustion, silent state loss, off-graph ad hoc scripting) that keeping retry as a real, bounded, inspectable graph edge is meant to avoid.

## 4. Fan-in merge strategy (merge-by-key vs named/indexed ports)

**Our decision:** Fan-in merges converging edges' outputs into one object keyed by field name; a key arriving with two conflicting types across edges is a lint error caught before any run. Named/indexed input ports are explicitly out of scope for v1.

**Findings:**

- **Apache Airflow (XCom)** — Positional/list pull with an optional string key, no static typing. `TaskInstance.xcom_pull(task_ids=['a','b'], key='return_value')` returns a list of values ordered exactly by the `task_ids` list, not merged into a keyed object; `key` defaults to `'return_value'` and is the same string for every task unless each task explicitly pushes under a distinct custom key via `xcom_push`. XCom values are pickled/JSON-serialized blobs with no schema and no engine-level type check across pushers — a consumer pulling `task_ids=['a','b']` gets whatever types each task happened to push, and any mismatch is discovered only at consumption time in Python, not statically. This is closer to *indexed-by-task-id* than either named ports or our merge-by-key: the "key" namespaces the whole XCom store, not the individual fields of a converging edge. Source: [Airflow XCom concepts](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/xcoms.html).
- **AWS Step Functions (`Parallel`/`Map`)** — Fan-in output is a raw JSON **array**, index-ordered to match `Branches[]` (Parallel) or the input array (Map's `ItemProcessor`), placed via `ResultPath` (defaults to `$`, replacing the whole input). There is no per-branch field name at all; branch 0's output lands at array index 0 regardless of its shape, and a downstream state must know branch order to destructure it (`$[0]`, `$[1]`, via `ResultSelector`). This is genuinely closer to **indexed ports** than to either named ports or merge-by-key — the array position *is* the port identity, and nothing merges same-named fields from different branches; they simply nest inside their own array slot, so a same-name/different-type collision that would be a lint error for us is structurally impossible for Step Functions (each branch's whole output stays isolated by index). Source: [Parallel state docs](https://docs.aws.amazon.com/step-functions/latest/dg/state-parallel.html), [ResultPath docs](https://docs.aws.amazon.com/step-functions/latest/dg/input-output-resultpath.html).
- **Argo Workflows** — Each template declares `outputs.parameters[].valueFrom.path` (or `.parameter`/`.expression`) with an explicit name, e.g. `single-output` bound to `/tmp/result.txt`. A fan-in consumer references `{{tasks.<TASK_NAME>.outputs.parameters}}` (the whole array of per-iteration output structs, JSON-serialized) or a specific `{{tasks.<TASK_NAME>.outputs.parameters.<NAME>}}` for one field. This is closer to **named ports** than merge-by-key: every parameter has one explicit producer-declared name and the consumer addresses it by that literal name (or the whole named-struct array), not by an inferred/collided key across multiple distinct upstream nodes. Argo has no engine concept of colliding two same-named parameters from two different upstream tasks into one object — each task's outputs stay namespaced under `tasks.<task-name>.outputs.parameters.<param-name>`, so there is nothing analogous to our key-collision lint check because the producer identity is always part of the address. Source: [Argo output-parameters walkthrough](https://argo-workflows.readthedocs.io/en/latest/walk-through/output-parameters/), [parameter-aggregation-dag.yaml example](https://github.com/argoproj/argo-workflows/blob/master/examples/parameter-aggregation-dag.yaml).
- **Temporal** — Not applicable at the engine level. `Promise.all(names.map(name => executeChild(childWorkflow, {...})))` in TypeScript workflow code (or the Go/Python/Java SDK equivalents) is ordinary language-level concurrency; the SDK returns a promise/future array in submission order, and combining/merging results into any shape (object, keyed map, custom struct) is entirely workflow-code logic with zero engine primitive for it. There is no fan-in construct, no key namespace, no port concept — Temporal treats "converging edges" as a pure application-code concern outside the orchestration layer. Source: [Temporal child workflows design pattern](https://docs.temporal.io/design-patterns/child-workflows), [TypeScript child-workflows guide](https://docs.temporal.io/develop/typescript/workflows/child-workflows).
- **Dagster (`@multi_asset` / asset dependency injection)** — This is the closest real analog to a *named-ports* rejection case. An asset function's Python parameter name is matched directly against an upstream asset key (`def clean_data(raw_users, raw_orders)` binds to assets literally named `raw_users`/`raw_orders`), or explicitly remapped via `": dg.AssetIn(key="raw-user-data")}` when the asset key isn't a valid Python identifier) — in effect, Python's own keyword-argument binding *is* a named-port system: the field name (parameter name) is the port, the schema is enforced by whatever consumes it in code, and two upstream assets can never collide on the same key because each is bound to its own distinct parameter slot, not merged into one shared object. Source: [Dagster assets API reference](https://docs.dagster.io/api/dagster/assets).
- **n8n (Merge node)** — Confirmed: the Merge node exposes fixed, numbered inputs (Input 1, Input 2, …) and a `mode` config with `Append` (stack items sequentially), `Combine → Matching Fields` (join by one or more named "Fields to Match", with Inner/Outer/Left/Right join semantics — this is the literal "merge by key" mode), `Combine → Position` (zip item N of Input 1 with item N of Input 2, no key involved), and `Choose Branch` (pass through exactly one input's data, discarding the rest). This is the one engine in scope that offers merge-by-key as a *choice* alongside indexed/positional and named-port-like branch selection, rather than making it the only option. Source: [n8n Merge node docs](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.merge/).

**Verdict:** Wrinkle — pure merge-by-key with no named-port escape hatch is rare among these six (only ours commits to it exclusively); Dagster's named-parameter binding and Argo's `valueFrom`-addressed named outputs both exist precisely because two upstream branches can legitimately produce same-named-but-semantically-different fields (e.g. two branches both naming an output `result` with unrelated meanings), which our lint would reject as a type collision even when the fields are intentionally distinct and never meant to merge.

## 5. DOT as the workflow definition format

**Our decision:** A `.dot` (Graphviz) file is the versioned source of truth for topology and bindings only; the `dot`/Graphviz binary is optional and never required to run a workflow.

**Findings:**

- **Graphviz itself** — the DOT grammar's `attr_stmt`/`a_list` production is `ID '=' ID [ ';' | ',' ] [a_list]`: a flat list of string-to-string pairs, with no nested object, array, or typed-value syntax anywhere in the language. This is not an implementation gap in any consuming tool — it is the language spec itself, so any engine wanting structured per-node config (JSON Schema, nested objects, enums) cannot express it in attributes without smuggling a serialized blob into a string value. Source: [DOT Language grammar, graphviz.org](https://graphviz.org/doc/info/lang.html).
- **Temporal** — official engineering rationale ("The fallacy of the graph," Temporal Voices blog, authored by Maxim Fateev, the creator of AWS SWF and Temporal's architect) argues explicitly against *any* graph/diagram notation — DOT, YAML DAGs, or drag-and-drop canvases alike — as a source-of-truth format, not merely against DOT specifically. It names three concrete failure modes: (1) control flow that depends on runtime data can't be drawn, only referenced via out-of-band expressions; (2) data passing degenerates into an untyped global key-value store or brittle JSONPath selectors across edges; (3) dynamic/data-dependent compensation (saga) paths become "an unmanageable monstrosity" to draw explicitly. Temporal's answer is ordinary Go/Java/Python/TS code plus Durable Execution (event-history replay), with zero declarative graph file at any layer. Source: ["The fallacy of the graph: Why your next agentic workflow should be code, not a diagram," temporal.io/blog](https://temporal.io/blog/the-fallacy-of-the-graph-why-your-next-workflow-should-be-code-not-a-diagram).
- **Apache Airflow** — the official DAG docs never mention `graphviz` or `.dot` in the context of authoring (confirmed by direct grep of the live docs page); Airflow's own "Best Practices" guide justifies the Python-file format specifically for dynamic DAG generation (`for` loops over table lists instead of repeating declarative blocks) and for reusing the ordinary Python toolchain (`mypy`, `pytest`, IDE refactoring) — i.e., the DAG file is executed as code, not parsed as a static graph document, which is the opposite direction from DOT (a pure static grammar with no execution semantics). Source: [Airflow DAGs core-concepts docs](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/dags.html), [Airflow Best Practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html).
- **LangGraph** — the graph is built exclusively through the `StateGraph` Python builder (`add_node`, `add_edge`, `add_conditional_edges`); there is no file format at all, declarative or otherwise. The library's own diagram export path goes through Mermaid or ASCII (`get_graph().draw_mermaid()`), and DOT only appears as a third-party bridge (via NetworkX/`pydot`) for visualization, never for defining the graph. Source: [LangGraph Graph API docs, docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/graph-api).
- **Argo Workflows** — the `Workflow`/`WorkflowTemplate` Kubernetes CRD is authored exclusively in YAML/JSON, with `dag.tasks[].dependencies` expressing the same edges DOT would. There is no parser in `workflow-controller` or the `argo` CLI that accepts `.dot`; the project's own repo only uses DOT/Go-diagrams as a documentation-generation dev-tool (`hack/docs/diagram.go`) to render Argo's *own architecture*, never to accept or emit a runnable workflow. Source: [Argo Workflows DAG template walkthrough](https://argoproj.github.io/workflows/), confirmed against [argoproj/argo-workflows GitHub issues #12634](https://github.com/argoproj/argo-workflows/issues/12634) and [#15351](https://github.com/argoproj/argo-workflows/issues/15351).
- **AWS Step Functions** — Amazon States Language is a JSON object (`States` map keyed by state name, `Next`/`Choice`/`Catch`/`Retry` fields) maintained as an open spec at states-language.net. ASL's `Retry` and `Catch` fields are structured JSON arrays of objects (error names, interval/backoff multiplier, max attempts) attached directly to a state — exactly the kind of nested, typed per-node configuration DOT's flat attribute strings cannot hold, which is why ASL never considered DOT. Source: [Amazon States Language spec, states-language.net](https://states-language.net/spec.html).

**Verdict:** Contradicts — no surveyed engine (LangGraph, Temporal, Argo, GitHub Actions, n8n, Prefect, Dagster, Airflow, AWS Step Functions) uses DOT as its authoring source of truth; every one uses either a general-purpose language (Airflow, Temporal, Prefect, Dagster, LangGraph's builder API) or a JSON/YAML document with native nested per-node fields (Argo, ASL, n8n, GitHub Actions). The gap is not pure unfamiliarity — Graphviz's own grammar is provably flat (`ID '=' ID` attributes only), so any format needing typed/nested per-node config structurally cannot live in DOT attributes, which is exactly why our design keeps DOT for topology+bindings only and pushes config to a companion markdown file. That specific split (declarative graph-topology file + separate per-node config file, config never inlined as graph attributes) has a real precedent in **Apache Oozie**, whose `workflow.xml` (control-flow DAG: `start`/`decision`/`fork`/`join`/action nodes) is deliberately kept free of environment values, which instead live in a sibling `job.properties` file — but Oozie's split is topology-vs-environment-parameters (dev/stage/prod swapping), not topology-vs-structured-per-node-schema/prose as ours is, and Oozie's DAG format is XML, not DOT. Source: [Oozie Workflow Functional Specification, oozie.apache.org](https://oozie.apache.org/docs/5.0.0/WorkflowFunctionalSpec.html). No engine we found pairs a Graphviz DOT file specifically with an external per-node config file the way our design does — that combination appears to be a genuinely novel pairing of a known idea (DOT for pure topology, attested nowhere as a *runtime* authoring format) with a known pattern (topology/config file separation, attested in Oozie with XML) that no one has previously assembled together.

## 6. Dynamic Fan-Out (N Parallel Instances, N Known Only at Runtime)

**Our decision:** No answer yet — dynamic fan-out (map-over-a-runtime-produced-list) is explicitly an open question for our static DAG, tracked separately from this locked design.

**Findings:**

- **Argo Workflows** — `withItems` vs `withParam`. `withItems` takes a JSON list written directly into the manifest (`withItems: ["apple", "banana"]`); it is fully known at parse time. `withParam` takes a JSON array *string*, typically `"{{steps.generate.outputs.result}}"` — the stdout of a prior step — and the manifest's `steps`/`dag` entry that carries `withParam` is written and lint-checked exactly once, as a single template invocation, regardless of runtime cardinality. Argo's own docs walk through generating the array in one step (`gen-number-list`, a Python script that JSON-dumps a list) and consuming it in the next via `withParam: "{{steps.generate.outputs.result}}"` — the length is unknowable until `generate` actually runs. The static manifest therefore has exactly one step definition for the loop body; the Argo controller (not the static spec) expands that single step into N pod nodes only once the referenced parameter resolves at execution time — this expansion is a live-run artifact (`status.nodes`), not something present in, or derivable from, the submitted YAML. Source: [Argo Workflows — Loops](https://argo-workflows.readthedocs.io/en/latest/walk-through/loops/).
- **AWS Step Functions — `Map` state (Inline vs Distributed)** — this is the cleanest precedent for "one static node, N runtime instances." The ASL `Map` state's static JSON definition never encodes N: `ItemsPath` (JSONPath, e.g. `$.users`) merely points at wherever the runtime input array will be; the state machine's `States` object, `ItemProcessor.States`, and every field are fixed text regardless of whether the array turns out to hold 3 items or 3 million. `MaxConcurrency` bounds concurrent iterations (Inline Map: hard cap of 40; Distributed Map: default 10,000, tunable up) but is a runtime throttle, not a count. Distributed Map is a genuinely separate `ProcessorConfig.Mode: DISTRIBUTED` (vs `INLINE`) added later specifically because Inline Map inherits the parent execution's 25,000-event history ceiling and 256 KiB payload limit — Distributed Map instead runs each iteration as an independent child *Map Run* execution with its own history, and can stream items straight from S3 via `ItemReader` without ever materializing the array in state input. Critically: adding Distributed Map required a new *execution* topology (child executions with separate histories), but it did **not** require any change to how the state machine's static definition is validated or authored — the `Map` state node is still one JSON object in one place in the ASL document. Source: [AWS Step Functions — Map state (Distributed mode)](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html).
- **Apache Airflow — Dynamic Task Mapping (`.expand()` / `.expand_kwargs()`)** — the single closest precedent to our exact situation. Airflow's own docs state it plainly: "dynamic task mapping defers task creation until runtime, allowing the scheduler to determine the exact number of task instances based on upstream task outputs... Right before a mapped task is executed the scheduler will create *n* copies of the task, one for each input." The Dag *graph view* renders the mapped task as a single node (`mapping_simple_graph.png` in the docs shows one box for `add_one.expand(x=[1,2,3])`, not three); the *grid view* is where the runtime-resolved instances appear individually, indexed by integer by default or by a Jinja-rendered name via `map_index_template` (e.g. an instance named `2024-01-01` instead of `0`). A safety valve, `max_map_length` (core config, default `1024`, added in Airflow 2.3.0), caps how large an XCom-pushed list/dict is allowed to be before triggering mapping; exceeding it fails the pushed task rather than exploding the scheduler. The DAG structure — one mapped task, one node — is identical whether the upstream returns 3 items or 1,000; only the *task instance* count (`map_index`) varies per Dag run. Source: [Airflow — Dynamic Task Mapping](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/dynamic-task-mapping.html); [Airflow — Configuration Reference, `max_map_length`](https://airflow.apache.org/docs/apache-airflow/stable/configurations-ref.html).
- **Temporal** — has no declarative fan-out-over-list primitive at all. There is no `Map` state, no `.expand()`, nothing analogous in the SDKs; Temporal's own "Fan-Out with Child Workflows" design-pattern doc shows the *entire* mechanism as an ordinary language `for`-loop (Python `while` / TypeScript `for`) that calls `workflow.start_child_workflow` (or `executeChild`) per chunk and then `asyncio.gather`/`Promise.all`s the handles — this is application code, not engine configuration. The doc's own constraints (chunk into batches, keep pending children per parent under ~2,000, keep event history under ~51,200, chunk-and-`continue_as_new` for huge N) are things the workflow author must hand-engineer, because Temporal has no static graph concept for the engine to reason about in the first place — a Temporal "workflow" is a deterministic program, not a declared topology, so "is the static graph still one node" is a category error for Temporal: there is no static graph to begin with. Source: [Temporal — Fan-Out with Child Workflows](https://docs.temporal.io/design-patterns/fanout-child-workflows).
- **Dagster — Dynamic Outputs (`DynamicOut`/`DynamicOutput`, `.map()`/`.collect()`)** — Dagster is the engine most explicit about the static/runtime split, and it draws the line exactly where our system would need to. The `@job` composition function (`pieces = load_pieces(); results = pieces.map(compute_piece); merge_and_analyze(results.collect())`) is static Python evaluated once at *definition* time — it contains exactly one call to `compute_piece` regardless of how many items `load_pieces` ultimately yields. Each `DynamicOutput` requires a `mapping_key` (a unique string per item); at runtime, Dagster's **execution plan** (a separate artifact from the **graph/job definition**) is the thing that resolves the dynamic keys and instantiates one execution step per key (e.g. displayed as `compute_piece[0]`, `compute_piece[1]` in the UI) — the *graph definition* stays fixed at one op, one edge; only the *execution plan*, built after the upstream op has actually run, is per-run-cardinality-dependent. `.collect()` is the fan-in counterpart, blocking until every dynamic clone completes before materializing a `list` for the aggregator op. Source: [Dagster — Dynamic graphs](https://docs.dagster.io/guides/build/ops/dynamic-graphs).
- **Prefect — `Task.map()`** — structurally different from the other five: Prefect has no separate declarative graph artifact to keep static in the first place. A `@flow` is an ordinary Python function; `.map()` is a method call that, when reached at *flow run* time, tells the engine to submit one task run per element of the iterable to the active Task Runner and return a `PrefectFutureList`. There is no compile-time or parse-time graph object analogous to Airflow's DAG or Dagster's job definition on which to ask "is this still one node" — the flow's shape is only knowable by actually executing the Python function, dynamic fan-out or not. Every mapped task run is nonetheless a first-class, individually observable unit in the Prefect UI (own state lifecycle, own retries/caching), so per-instance observability is preserved even without a preserved *static* graph. Source: [Prefect — Tasks](https://docs.prefect.io/v3/concepts/tasks).
- **LangGraph — `Send` API** — the most direct confirmation of "one static node, runtime-only multiplication." `Send(node: str, arg: Any)` is returned in a list from a conditional-edge router function (`return [Send("generate_joke", {"subject": s}) for s in state["subjects"]]`); `subjects` is only known once the graph starts running. The compiled graph's own `get_graph().draw_mermaid()` output for this exact map-reduce pattern renders a single `generate_joke` node with one dynamic edge in from `__start__` (rendered as a dashed `-.->` conditional edge in the Mermaid output) — never N nodes, never a node per subject. `Send` is purely a *runtime dispatch* mechanism: it does not touch the compiled `StateGraph`'s topology at all, it only changes what state gets routed to the (singular, statically-declared) `generate_joke` node on a given invocation, once per `Send` in the returned list. Source: [LangGraph — `Send` reference](https://reference.langchain.com/python/langgraph/types/Send); [LangGraph — Graph API / map-reduce](https://docs.langchain.com/oss/python/langgraph/graph-api).

**Synthesis:** Across all seven, the dominant, load-bearing pattern is unambiguous: **the static definition keeps exactly one node/state/task/step representing the fan-out point, and only the runtime execution — pods (Argo), child workflow executions or Map Runs (Step Functions), task instances distinguished by `map_index` (Airflow), execution-plan steps keyed by `mapping_key` (Dagster), or dispatched `Send` invocations (LangGraph) — multiplies.** Step Functions is the cleanest proof this is possible with zero compromise: the ASL `Map` state's JSON is byte-identical whether N is 1 or 1,000,000; `ItemsPath` names *where* the array will be, never *how big* it is. Airflow is the closest architectural match to us (an explicit DAG object, parsed and rendered before any run) and it never abandons static analysis for this — the scheduler still parses one DAG with one mapped-task node; it only defers *instance* creation, bounding runaway cardinality with a config guardrail (`max_map_length`) rather than a topology change. Dagster is the most explicit that this requires a two-tier model: a static graph/job definition (fixed) plus a separate runtime execution plan (cardinality-dependent) — this is very likely the shape our engine would need to add: a `.dot` graph that stays exactly as authored, plus a runtime "instance plan" our Bun scripts compute once N is known, mirroring how our nodes already separate topology (DOT) from per-node config (markdown). LangGraph confirms the same split holds even for a code-first, non-declarative-YAML engine: `Send` never mutates `get_graph()`'s output. The two outliers — Temporal and Prefect — are not counterevidence to this pattern so much as proof it's optional to have a static graph at all: neither preserves a declared topology to keep static, because neither has one in the first place (workflow authoring is bare code); Temporal in particular offers no declarative construct whatsoever and pushes all of chunking, concurrency-bounding, and history-limit management onto the workflow author. For our system, this strongly suggests dynamic fan-out is answerable **without** abandoning static DOT analysis: the `.dot` file keeps one node with, e.g., a `fanout=true` attribute or an `[on="item"]`-style self-consistent edge shape; lint continues to validate the single node's schema (width-subtyping already handles "N producers of the same shape" for free, since every fanned-out instance produces an identical schema by construction); and a new runtime-only concept — an execution/instance plan, analogous to Dagster's — is what actually enumerates N instances once an agent reports the runtime-produced list, exactly mirroring how Argo's controller, Step Functions' Map Run, and Airflow's scheduler expand a single static node into N tracked runtime units after the array is known.
